# `reports/` —— 验证证据的保存纪律

> **性质**：本目录存放**可复核的验证证据**。
> 它是"某次验证实际发生了什么"的记录，**不是**能力声明、**不是**路线图、
> **不是**设计文档。
>
> 本文件定义**证据范围、保存纪律与产物边界**。所有放入本目录的记录必须遵守。

---

## 1. 为什么需要本目录

本仓库此前的验证结论以**叙述性断言**形式散落在 `docs/*.md` 中，例如
"ARM VERIFIED 6/6 PASS"。问题在于：

- 支撑脚本与日志存放于 `tmp/audit/`，而 `tmp/` 被 `.gitignore` 忽略
  ⇒ **换一台机器无法只靠仓库复现**（`scripts/repro/README.md` 已自述此问题）；
- 没有退出码、没有时间、没有环境、没有原始输出位置；
- 因此历史 PASS **只能作为线索，不能作为当前证据**。

本目录的作用：把"结论"升级为"**带 SHA + 命令 + 退出码 + 分类 + 输出位置**的记录"。

> **核心规则**：**未实际执行的测试，一律记为 `NOT_RUN`，禁止推测其结果。**
> 历史记录不得当作当前证据。

---

## 2. 证据范围（什么该进、什么不该进）

### 2.1 应当进版本库（体积小、无敏感、可 review）

- 验证的**基线提交 SHA** 与**验证提交 SHA**
- 执行的**命令**、**退出码**、**结果摘要**
- **运行环境**：OS / 内核 / Python / 关键工具版本
- **CI Run ID、URL、工作流名、Job/Step 逐项结果**
- 每项结论的**分类**（见 §4）
- **原始输出的保存位置**与**可访问期限**
- `NOT_RUN` / `BLOCKED` 项的**原因**

### 2.2 禁止进版本库

遵守仓库既有 `.gitignore` 边界，**不得**为使本目录"看起来完整"而提交：

| 类别 | 原因 |
|---|---|
| 固件 / 镜像（`*.bin` `*.img` `*.squashfs` `*.jffs2` `*.ubifs`） | 体积 + 授权 + `.gitignore` 已排除 |
| PCAP / BLF 抓包 | 体积；`pcaps/` 已排除 |
| fuzz 逐例语料（`fuzz-out/`） | 体积巨大；已排除 |
| `tmp/audit/` 的全部历史内容 | 体积 + 历史快照；**不回填** |
| 任何凭据、token、私钥、`.env` | 安全 |
| 大型日志的完整副本 | 由 CI 保留并提供 URL |

> **原则**：证据**引用**原始产物的位置，而不是**搬运**原始产物。
> 需要长期留存的大产物应通过 CI artifacts（有保留期限）或本地归档，
> 并在证据文件中**注明其位置与期限**。

## 3. 三类载体的分工

| 载体 | 存什么 | 保留 | 为什么 |
|---|---|---|---|
| **Git 跟踪文本**（本目录） | SHA、命令、退出码、分类、结论、NOT_RUN、输出位置 | 永久（随版本） | 体积极小、可 review、可追溯 |
| **CI 日志** | 完整 stdout/stderr | GitHub 默认期限（约 90 天） | 由平台保留，URL 可查 |
| **CI artifacts** | 生成的大产物 | 有期限，可配置 | 体积大，无需入库 |

**证据文件必须写明原始输出落在哪一类**，以及**过期后如何重跑**。

---

## 4. 结论分类（强制）

每一项测试/验证**必须**被归入且仅归入以下一类：

| 分类 | 含义 |
|---|---|
| `PASS` | **本轮实际执行**且通过。必须有命令 + 退出码。 |
| `FAIL` | **本轮实际执行**且失败。 |
| `BLOCKED` | 因**前置条件缺失**（环境/依赖/权限）无法执行。必须写明缺什么。 |
| `UNKNOWN` | 无法判定（如产物已被清理、结论依赖不可得信息）。 |
| `NOT_RUN` | **本轮未执行**。禁止填写任何推测结果。 |

### 4.1 三条不得混淆的来源

正式证据记录**必须**区分下列三者，**不得**折叠为一个总体 PASS：

```
本地等价复现      —— 在本机以等价方式执行的步骤（如逐文件独立进程复现 qa_fast.sh）
远程 CI 实际执行   —— GitHub Actions 上真实运行的 Job/Step（须给 Run URL）
因前置条件失败而未执行 —— 上游步骤失败导致后续被 skip（须逐项列出 skipped）
```

> 例：某次 CI 中 `Bring up vcan0` 失败 ⇒ 其后 `Extended quality gate` 为
> **未执行**，**不得**因为该 workflow 曾经"success"而记为 PASS。

## 5. 文件命名与模板

```
reports/
  README.md                          ← 本文件
  EVIDENCE_TEMPLATE.md               ← 通用模板（复制后填写）
  <OQ-id>_<date>_evidence.md         ← 该 OQ 的首次验证
  <OQ-id>_<date>_<round>_evidence.md ← 后续轮次（如修订后复验）
```

- `<OQ-id>`：如 `OQ-1`、`OQ-2`、`C3-A3`
- `<date>`：`YYYY-MM-DD`（本地时区需注明）
- `<round>`：可选轮次标识，如 `f1`（针对审查发现 F-1 的修订轮）
- 一份文件对应**一次验证活动**，而非一个阶段的所有活动

**多轮验证的纪律**：

- 后续轮次**必须新建文件**，**不得覆盖**前一轮记录；
- 每份文件须在开头注明**适用范围**（对应哪个提交 SHA / 哪一轮），
  并链接到相邻轮次，避免读者把旧轮次结果误当作新轮次结果；
- 轮次之间若结论发生变化（例如某失败已修复），**在各自文件内如实记录**，
  不改写历史文件。

模板见 [`EVIDENCE_TEMPLATE.md`](EVIDENCE_TEMPLATE.md)。

## 6. 隐私与安全边界

- **不得**记录任何凭据、token、私钥、cookie、API key。
- **不得**记录可能含敏感信息的主机名、内网地址、真实设备标识。
- 环境描述写到"OS + 版本 + 工具版本"即可，不必写用户目录全路径。
- 安全实验默认边界不变：仅 `vcan0` / 虚拟 ECU / 本地环境；
  不涉及真实 CAN / ECU / 车辆。

---

## 7. 与门禁的关系（重要区分）

本目录解决的是"**证据可复核**"。

它**不**解决"**门禁自动重跑**" —— 后者属独立工作项（NQ-11）。
放入本目录的记录**不构成**任何门禁，也不会因为存在而让 CI 变绿。

同样，本目录**不**替代 `docs/` 中的设计文档与阶段报告：
- `docs/` = 设计、决策、阶段结论（**为什么**）
- `reports/` = 某次验证的原始事实（**实际发生了什么**）
